Authentication and authorization

Authentication establishes identity or verifies credentials. Authorization determines whether that caller may perform an action on a specific resource. Both must be enforced server-side; hiding a client control is insufficient.

Bearer access tokens can be sent in an Authorization header. Anyone possessing a bearer token can use it, so protect it in transit and storage. Use HTTPS, avoid putting tokens in URLs, and do not publish credentials in examples or logs.

OAuth 2.0 is an authorization framework; it is not, by itself, a user authentication protocol. API keys may identify an application or project and should not automatically be treated as proof of a user's identity.

Check resource access every time

Possessing a valid token does not mean the caller may read every project. Check permissions for the requested object and operation. CORS is a browser policy, not a substitute for authorization.

References: RFC 6750 — Bearer tokens and RFC 6749 — OAuth 2.0.

API versioning

Versioning communicates breaking contract changes. A path such as /v1/projects is an easy-to-read convention; header or media-type strategies are alternatives. HTTP does not require one universal API versioning scheme.

Choose a strategy deliberately, document compatibility guarantees, announce deprecations, and provide a migration window. Even adding a field may break clients that assume a closed schema, so test consumer expectations rather than assuming every additive change is harmless.

Error-handling conventions

Return an appropriate HTTP status and a predictable body. RFC 9457 defines problem details, commonly sent as application/problem+json, with members such as type, title, status, detail, and instance.

Use stable problem types for client logic, rather than asking clients to parse human-readable messages. The optional status member should match the actual response status when present. Define extensions for field validation when needed.

Describe the problem usefully without exposing stack traces, secrets, internal infrastructure, or sensitive records. Correlation identifiers can help support teams find detailed server-side logs.

Reference: RFC 9457 — Problem Details for HTTP APIs.

API best practices

The following are design recommendations for this guide, not mandatory REST naming rules:

  • Use consistent resource names and document method semantics.
  • Validate input types, sizes, ranges, and allowed operations.
  • Apply access checks to resources and returned fields.
  • Document successful, empty, invalid, unauthorized, and unavailable outcomes.
  • Bound collection sizes and expensive operations.
  • Specify time formats, ordering, null behavior, and compatibility policies.
  • Test contracts and observe failures while redacting sensitive data.

Pagination

Return a bounded slice of a collection. Offset pagination can be straightforward, but insertions or deletions between requests can shift results. Cursor pagination uses a continuation value tied to a documented ordering and can better suit changing collections.

A contract might return data and next_cursor. This shape is illustrative, not a universal standard. Define page-size limits, deterministic sorting with a tie-breaker, how filters interact with cursors, and how the client recognizes the end. Snapshot guarantees require explicit server support.

Rate limiting

Rate limits bound request volume under a documented policy, such as requests per account per time window. A server can return 429 Too Many Requests and may include Retry-After. That field can specify a delay in seconds or an HTTP date.

Clients should respect retry guidance, cap retries, and use backoff with jitter where appropriate. A retry still needs to account for the operation's idempotency. Document limits and avoid assuming that every API exposes the same quota headers.

References: RFC 6585 — 429 and RFC 9110 — Retry-After.
