HTTP & REST

A shared protocol. A deliberate architectural style.

HTTP fundamentals

HTTP uses a request–response model. A client addresses a resource and expresses intent through a method; a server communicates the result through status, headers, and optional content. HTTP semantics are shared across protocol versions, while their wire formats differ.

Resource identifiers and representations serve different purposes: /projects/42 identifies a resource, while JSON might describe its current state. A representation is not necessarily a database row.

Reference: RFC 9110 — HTTP Semantics.

REST architecture

REST—Representational State Transfer—is an architectural style defined through constraints, not a synonym for JSON over HTTP.

Client–server
Separate interface concerns from data and service concerns.
Stateless
Each request supplies the context needed to understand it.
Cacheable
Responses identify whether reuse is permitted, supporting efficiency.
Uniform interface
Use resource identification, representations for manipulation, self-descriptive messages, and hypermedia to guide application transitions.
Layered system
Clients need not know whether an intermediary or origin server handles an interaction.
Code on demand (optional)
A server may extend client behavior by supplying executable code.

Hypermedia means responses can provide links or controls for the next available action. An API using resource-oriented URLs but omitting this constraint may be better described as an HTTP API rather than claiming full REST adherence.

Reference: Fielding — REST architectural constraints.

Stateless communication

A request should not require the server to remember a previous conversational step in order to interpret it. Include the resource identifier, credentials when needed, and applicable request data.

Stateless does not mean storage-free

A server can persist projects, accounts, and other resource state. The constraint concerns client session context between requests, not the absence of a database.

For example, retrieving a project should identify that project and supply required access information without depending on a preceding “select project” request.

Reference: Fielding — Stateless constraint.
